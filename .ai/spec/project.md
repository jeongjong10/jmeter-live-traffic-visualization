# JMeter 실시간 부하 흐름 시각화 도구 기획서 (JMeter Live Traffic)

JMeter로 구성한 비즈니스 프로세스(사용자 흐름) 테스트가 실행되는 동안, 가상 사용자가 어느 단계에 있고 지연·오류가 어디에서 생기는지를 화면에서 실시간으로 관제하고, 끝난 실행을 다시 재생해 분석하는 도구다.

이 기획서는 노션 페이지와 저장소 `.ai/spec/project.md`에 같은 내용으로 둔다. 작업 상태·수용 기준·증거의 정본은 기획서 하위의 실행 작업 큐다.

---

## 1. 해결하려는 문제

부하 테스트 사용자는 JMeter에서 로그인 → 조회 → 처리 → 결과 확인처럼 업무 순서를 따르는 테스트 계획(jmx)을 만들고 여러 가상 사용자로 반복 실행한다. JMeter가 기본으로 보여 주는 것은 Sampler별 처리량·응답시간·오류율 같은 집계 수치와 결과 목록이어서, 실행 중에 다음 질문에 답하기 어렵다.

1. 지금 가상 사용자들은 업무 흐름의 어느 단계에 있는가.
2. 어느 API가 평소보다 느려지고 있는가.
3. 지연이나 오류는 언제, 어느 단계에서, 왜 발생했는가.
4. 테스트가 끝난 뒤 그 흐름을 시간순으로 다시 볼 수 있는가.

이 도구는 JMeter 실행 결과를 데이터 원천으로 삼아 이 질문들에 화면으로 답한다.

---

## 2. 목표와 산출물

### 2.1 목표

1. 기존 jmx를 고치지 않고 Backend Listener 하나만 추가해 연동한다.
2. 실행 중 가상 사용자의 업무 단계 위치와 단계별 응답시간·지연·오류를 실시간으로 표시한다.
3. 실행이 끝나면 같은 흐름을 시간축으로 재생·탐색한다.
4. 사용자는 주소 하나(`http://127.0.0.1:8765`)로 진입해 실시간 관제와 재생을 모두 사용한다.
5. 실제 측정값과 시각적 표현을 구분한다.

### 2.2 산출물

| 산출물 | 위치 | 기술 | 역할 |
| --- | --- | --- | --- |
| 리스너 JAR | `src/listener` | Java 21, Maven | JMeter `lib/ext`(또는 `user.classpath`)에 넣는 Backend Listener. 샘플 결과를 계약 JSON으로 정규화해 배치 전송하고, 테스트 시작 시 실행 중인 테스트 트리를 전송하며, 실패 샘플의 사유를 수집한다 |
| collector | `src/collector` | Python 표준 라이브러리 | 이벤트 수신, jmx 해석, 사용자 위치 복원, 실행 기록 보관, SSE 실시간 전송, 빌드된 화면 제공을 하나의 프로세스로 수행한다 |
| 화면 | `src/web` | React, TypeScript, Vite, Canvas | 대시보드형 관제·재생 화면. NetViz(MIT, Yuval Avidani)에서 파생 |
| 검증 자산 | `tests/` | Python, JMeter, sh, vitest | collector·화면 계산 단위 테스트, 모의 API와 예제 jmx로 실행 결과와 화면 데이터의 일치를 확인하는 E2E |

## 3. 범위

### 3.1 포함

- JMeter Backend Listener 기반 샘플 단위 실시간 수집
- 실행 중인 테스트 트리(jmx) 해석과 Thread Group별 단계 목록 구성
- 스레드 이름·라벨·시작 시각을 이용한 가상 사용자 위치 복원
- 단계별 1회 호출 응답시간(평균·p95), 평소 대비 지연, 동시 사용자, 처리량, 오류와 실패 사유 표시
- 최근 실행 기록 보관과 시간축 재생·요청 단위 이동
- 단일 머신 loopback 환경에서의 실행

### 3.2 제외

- 서버 내부 호출 경로·DB 쿼리 단위 분석 (JMeter가 관측하지 않는 영역)
- 여러 JMeter 실행기(분산 테스트)의 통합 관제
- 인증·TLS·원격 노출, 재시도·멱등 전송, 장기 보존 관리
- 요청·응답 본문과 헤더 수집 (개인정보 포함 가능성)
- 자동 부하 제어와 테스트 중단

## 4. 사용 흐름

1. 사용자는 JMeter에서 업무 흐름을 Thread Group과 Sampler 순서로 구성한다. 이 구성이 곧 화면의 단계 목록이 된다.
2. 리스너 JAR을 JMeter에 넣고 Test Plan에 Backend Listener를 하나 추가한다. 구현 클래스는 `io.axtutorlog.jmeter.backend.EventCollectorBackendListener`, 인자 `collectorUrl`은 `http://127.0.0.1:8765/events`다.
3. `docker/`에서 `docker compose up -d`로 시스템을 띄우고 `http://127.0.0.1:8765`를 연다. 테스트 계획이 아직 없으면 화면은 위 연결 방법을 안내한다.
4. JMeter 테스트를 시작하면 리스너가 실행 중인 테스트 트리를 collector에 보내고, collector는 새 실행 기록을 연다. 화면은 실시간으로 갱신되고, 테스트가 끝나면 실시간 모드는 마지막 시점에서 멈춘다.
5. 사용자는 상단 **실행 기록**에서 지난 실행을 골라 재생·탐색한다. 리스너 없이 기록만 볼 때는 **jmx 선택**으로 계획을 직접 등록할 수 있다.

## 5. 시스템 구성

### 5.1 전체 구조

```
 [JMeter 실행 환경]                            [collector 컨테이너: 127.0.0.1:8765]
┌────────────────────────────┐  POST /events   ┌──────────────────────────────────┐
│ JMeter (GUI 또는 -n)       │  POST /api/     │ 수신·정규화                      │
│  ├ 사용자 jmx (무수정)     │    test-tree    │ jmx/테스트 트리 해석 (jmx_plan)  │
│  └ Backend Listener JAR ───┼───────────────▶ │ 사용자 흐름 복원 (flow_tracker)  │
│     비동기 큐·배치 전송     │                 │ 실행 기록 보관   (run_store)     │──▶ Docker 볼륨
└────────────────────────────┘                 │ 실시간 전송      SSE /stream     │      runs/<id>/
                                               │ 로그             logs/collector  │
                                               │ 화면 제공        /app/web        │
                                               └───────────────┬──────────────────┘
                                                               │ 같은 주소 (/, /collector/*)
                                               ┌───────────────▼──────────────────┐
                                               │ 브라우저: JMeter Live Traffic    │
                                               │ KPI·시간축 그래프·업무 흐름·표   │
                                               └──────────────────────────────────┘
```

### 5.2 실행 구조

- 시스템은 collector 컨테이너 하나다. `docker/`에서 `docker compose up -d`를 실행하면 이미지 빌드 단계에서 화면을 만들고, collector가 API·SSE와 화면을 같은 포트로 제공한다. 화면은 API를 `/collector/...`로 호출하고 collector는 이 접두어를 떼고 처리한다.
- 컨테이너 포트는 호스트의 `127.0.0.1`에만 노출한다.
- 화면 개발 시에는 Vite 개발 서버(5174)를 추가로 띄워 HMR을 쓰며, API 호출은 collector로 프록시된다.
- 리스너 JAR은 JMeter 쪽 산출물이므로 Maven으로 빌드해 JMeter에 넣는다.

환경변수는 두 계층으로 나누고, OS 환경변수 `COMPOSE_ENV_FILES`(예: `.env.dev`)로 환경을 고른다.

| 계층 | 파일 | 키 | 의미 |
| --- | --- | --- | --- |
| 컨테이너 기동 | `docker/.env.*` | `COMPOSE_PROJECT_NAME` | Compose 프로젝트명(컨테이너·볼륨 이름 접두어) |
| 컨테이너 기동 | `docker/.env.*` | `COLLECTOR_PORT` | 호스트 진입 포트(기본 8765) |
| 런타임 | `items/.env.*` | `COLLECTOR_RUN_KEEP` | 보관할 최근 실행 기록 수(기본 5) |

로그는 저장소 루트 `logs/`에 모은다(collector 로그 `logs/collector/collector.log`, E2E 실행 로그와 JTL `logs/e2e/<시나리오>/`). 실행 기록과 등록 계획은 Docker 볼륨에 보관한다.

### 5.3 디렉토리 구조

```
.ai/            AI 협업 파일, spec/ 명세 문서 (본 기획서, 이벤트 계약, 검증 결과, 설계서)
docker/         Compose 진입점·서비스 정의·Dockerfile, 컨테이너 기동용 .env.*
items/          런타임 환경변수 (.env.example만 커밋)
src/listener/   Backend Listener (Maven, 테스트 포함)
src/collector/  collector
src/web/        화면
tests/          collector 단위 테스트, web 계산 로직 테스트, e2e (checkout-flow, btoc-like, listener)
logs/           collector 로그, E2E 로그·JTL (Git 제외)
```

## 6. 데이터 수집과 흐름 복원

### 6.1 수집 방식

실시간 수집은 커스텀 `BackendListenerClient`가 `SampleResult`를 비동기로 받아 짧은 배치로 collector에 보내는 방식이다. JTL 파일 tail은 기본 설정에서 flush가 꺼져 있어 실시간 반영이 늦고, 기본 Graphite/InfluxDB 리스너는 지표 집계 중심이어서 샘플 단위 흐름 복원에 맞지 않는다. 원본 JTL은 정확도 대조 기준으로 쓴다.

- 리스너는 샘플 결과를 비동기 큐에 모아 `batchSize`(기본 100) 또는 `flushIntervalMillis`(기본 1000ms) 단위로 `POST /events`에 보낸다. 전송은 at-most-once이며, 실패한 배치는 중복을 막기 위해 로그만 남기고 버린다.
- 전송 필드는 시각·경과 시간·라벨·스레드 이름·성공 여부·응답 코드·latency·connect·송수신 바이트 등 19개다. 실패한 샘플에 한해 Assertion 실패 메시지(없으면 응답 메시지)를 앞 200자까지 보낸다. 성공 샘플과 응답 본문·헤더는 보내지 않는다.
- 테스트 시작 시 JMeter가 보유한 테스트 트리(GUI에서 저장하지 않은 변경·비활성화 포함)를 `POST /api/test-tree`로 보내고, 시작·종료 표시를 보낸다.
- collector → 브라우저 실시간 전달은 SSE(`/stream`)다. 이벤트를 묶어(`batch`) 보내고, 화면이 밀리면 `resync`로 전체 재로딩을 지시하며 이벤트를 버리지 않는다.

요청 형식과 이벤트의 상세는 `.ai/spec/event-contract.md`에 둔다.

### 6.2 흐름 복원

1. collector는 테스트 트리를 해석해 활성 Thread Group별 단계 목록(트리 위치 기준, 같은 라벨은 위치로 구분), 반복 단계(↻), 부하 설정(사용자 수·Ramp-up·루프·지속 시간 등), 오류 시 동작(`on_sample_error`)을 만든다.
2. 각 결과의 스레드 이름·라벨·시작 시각으로 그 가상 사용자의 단계 위치를 복원한다.
3. 한 결과가 도착하면 같은 사용자의 다음 단계를 **처리 중(추정)**으로 표시하고, 실제 결과가 오면 실측으로 확정한다. 실패 이후의 표시는 jmx의 오류 시 동작(continue·stoptest 등)을 따른다.
4. 이벤트는 실행 기록(`runs/<id>/events.ndjson`, 당시 계획은 `meta.json`)에 남는다. 테스트가 시작될 때마다 새 기록을 만들고 최근 N개(기본 5)를 보관한다. 각 기록은 당시 계획 기준으로 그린다.

지원하는 테스트 요소는 HTTP Sampler, Loop Controller, If Controller, Flow Control Action이며, 그 외 요소는 화면에 경고로 표시한다.

## 7. 화면 구성

화면 이름은 **JMeter Live Traffic**이다. 위에서부터 다음 순서로 배치한다.

| 영역 | 내용 |
| --- | --- |
| 고정 영역 | 스크롤해도 남는다. 제목·실행 기록·Thread Group·jmx 선택 줄, KPI 줄(상태·활성 사용자·처리량·p95·오류율), 재생 조작부, 전체 단계 요약 줄 |
| 쓰레드 속성 | Thread Group 설정(사용자 수, Ramp-up, 루프, 동일 사용자, 생성 지연, 생명주기, 지속 시간, 시작 지연, 오류 시 동작)과 의미, 이번 실행의 실측값 |
| 시간축 그래프 | 사용자가 선택한 그래프만 표시(선택은 브라우저에 기억). 기본은 활성 사용자·처리량·응답시간(p50/p95)·오류. 추가로 사용자 수 대비 처리량·p95, 응답시간 구성(연결·서버 대기·수신), 응답 코드별 건수, 응답시간 백분위, 오류율. 클릭하면 그 시점으로 이동 |
| 오류 요약 | 단계·응답 코드·실패 사유별 |
| 업무 흐름 | 두 보기 전환: **단계 흐름**(사용자 토큰이 업무 단계를 따라 이동)과 **요청·응답 왕복**(JMeter와 각 API 사이의 요청·응답). 두 보기는 같은 시각 규칙을 쓴다. 위에 접을 수 있는 **보는 법** 범례 |
| 표 탭 | 집계 보고서(JMeter Aggregate Report 항목), 결과 트리(행 클릭 시 그 시점으로 이동), 사용자 타임라인, 단계×시간 히트맵(동시 사용자·처리량·1회 평균 응답시간·오류 중 선택) |

- **재생 조작부**는 실시간, 처음부터, 재생/일시정지, 재생 바, 속도를 한 덩어리로 둔다. 재생 속도는 0.05×~2×(기본 0.25×)이고 ←/→ 키로 요청 하나씩 넘겨 볼 수 있다. 실시간 모드는 리스너 전송 간격을 감안해 1.5초 늦게 그리고, 테스트 종료 시점에서 멈춘다. 재생 중 타임라인 조작은 재생을 유지하고, 정지 중 조작은 재생 버튼을 눌러야 진행한다.
- **전체 단계 요약 줄**은 모든 단계를 한 칸씩 보여 준다. 숫자 = 처리량(req/s), 칸 색 = 평소 대비, 빨간 점 = 오류. 칸을 누르면 그 단계를 선택하고 흐름 화면을 그 단계로 옮긴다.
- 단계 노드·점에 마우스를 올리면 상세가 보이고, 클릭하면 단계 선택·사용자 여정 강조가 된다.
- **테마**는 다크/라이트/시스템을 지원하며 화면 오른쪽 위에 떠 있는 별도 선택이다. 그래프와 캔버스 색도 테마를 따른다.
- 시각 효과(색·수치·토큰)의 설명은 줄글이 아니라 견본 + 이름 + 한 줄 의미의 시각 범례로 한다.
- 화면의 모든 HTML 요소는 `jlt-`로 시작하는 고유 id를 가진다(`jlt-<영역>-<부분>`, 반복 요소는 단계 id·순번을 붙임). 사용자가 요소를 특정해 지시할 수 있게 하기 위함이다.

## 8. 시각 표현 규칙

### 8.1 측정값과 추정 표현

- 화면의 수치(처리량·응답시간·오류)는 JMeter가 측정한 샘플 결과에서만 계산한다.
- 다음 단계의 **처리 중** 표시는 응답 전 상태를 알 수 없는 Backend Listener의 한계를 보완하는 추정이며, 점선으로 실측과 구분한다.
- 토큰 이동 같은 애니메이션은 읽기 위한 시각 표현이며 실제 요청 수를 뜻하지 않는다.

### 8.2 단계 수치

- 응답시간은 **1회 호출 기준**(평균·p95)이다. 같은 사용자가 반복 단계를 여러 번 호출해도 호출 1회의 응답시간으로 계산한다. 반복을 누적한 체류 시간은 그 API의 평가를 왜곡하므로 쓰지 않는다. 반복 횟수는 전체 호출 수와 사용자 1명당 평균 호출 수로 따로 보여 준다.
- 동시 사용자(지금 그 단계 응답을 기다리는 서로 다른 가상 사용자 수)와 처리량(최근 1초 완료 수)은 숫자로 표시하고 색과 분리한다.

### 8.3 노드 색: 평소 대비

노드 색은 **"이 API가 이번 실행의 평소보다 느려졌다"**를 뜻한다. 다른 API와 비교하지 않는다.

| 항목 | 정의 |
| --- | --- |
| 평소 | 그 API가 이번 실행에서 지금까지 끝낸 요청 응답시간의 중앙값. 20ms 미만은 20ms로 본다 |
| 지금 | 최근 2초에 끝난 요청의 응답시간과 처리 중인 요청의 경과 시간을 합친 중앙값 |
| 평소 대비 | 지금 ÷ 평소. ×1.2 이하 파랑 → ×1.6 주황 → ×2 이상 빨강 |
| 색 없음(회색) | 끝난 요청 5건 미만(평소 없음), 또는 최근 2초에 끝난 요청도 처리 중인 요청도 없음 |

사용자가 몰리기만 하고 응답이 평소대로인 단계(예: 반복 단계)는 파랑이다. 목표 응답시간 같은 절대 기준이나 다른 실행과의 비교는 쓰지 않는다.

### 8.4 상태별 표현

- **실행 완료 상태**: 테스트가 끝나고 재생 위치가 기록 끝이면 마지막 순간 값 대신 각 단계의 최대치(최대 동시 사용자, 1초 구간 최대 처리량, 평소 대비 최대, 최종 평균·p95·오류)를 정적으로 표시하고 사용자 토큰은 그리지 않는다. 평소 대비 최대는 재생 중과 같은 계산을 실행 전체에 걸쳐 훑은 최대값이어서 재생 중 어느 시점 값보다 작지 않다. 재생 위치를 앞으로 옮기면 그 시점 값으로 돌아간다.
- **비교 배지**(평균 최대, p95 최대, 오류 건수·비율)는 테스트가 끝난 뒤 최종 결과 기준으로만 단다. 실행 중에는 오류 건수만 노드에 글자로 보인다.
- **사용자 토큰**: 처리 중·지연 토큰은 크기가 맥동해 살아 있는 상태를 보인다(지연은 더 빠르고 크게).
- **색 절제**: 모든 API는 한 가지 색이고, 색은 상태에만 쓴다(평소 대비 = 파랑→주황→빨강, 오류 = 빨간 글자·점, 선택 = 흰 테두리).

## 9. 비기능 요구사항

- 시각화가 JMeter 테스트 성능에 영향을 주지 않도록 리스너는 비동기 큐와 배치 전송을 쓴다.
- 대량 실행에서 화면이 멈추지 않아야 한다. collector는 이벤트를 묶어 보내고, 화면은 이벤트를 증분 반영하며 무거운 계산은 초당 4회, 사용자 타임라인은 캔버스로 그린다. 고부하에서 토큰은 표본만 그리고 수치는 전체 결과로 계산한다.
- 데이터 수집 실패와 화면 연결 끊김을 구분해 표시한다.
- 실행 기록으로 실시간과 같은 흐름·지표를 재현한다.
- collector는 loopback에만 노출한다. 인증·TLS·입력 제한·전달 보장을 갖추기 전에는 호스트 밖으로 노출하지 않는다.

## 11. 대안 형태

현재 형태는 **웹 화면 하나와 리스너 JAR 하나**다. 다음 두 형태는 설계서만 두고 구현은 별도로 진행한다.

- 웹에서 JMeter 실행: 화면에서 jmx를 올리고 실행 버튼으로 JMeter(-n)를 띄워 구성 → 실행 → 관제 → 재생을 한곳에서 한다. `.ai/spec/design-web-jmeter-runner.md`
- JMeter 내장(GUI) 플러그인: JMeter GUI 안에서 관제 화면을 연다. `.ai/spec/design-jmeter-gui-plugin.md`

## 12. 한계와 미결 사항

### 12.1 한계

- 관측 범위는 JMeter가 호출한 요청 결과다. 서버 내부 흐름은 별도 계측 없이는 그리지 않는다.
- 단일 JMeter 실행기, loopback, at-most-once 전송을 전제로 한다.
- 처리 중 표시는 다음 결과가 올 때까지의 추정이다.

### 12.2 미결 사항

- 1초 버킷 집계와 화면 반영 지연·테스트 간섭 측정
- 기준 실행(무부하 실행 등) 대비 비교 방식
- Java 패키지명(`io.axtutorlog.jmeter.backend`) 변경 — 기존 jmx의 리스너 클래스명에 영향
- 원격 노출 시 인증·전달 보장 설계

## 13. 운영 기준

- 이 기획서와 하위 실행 작업 큐가 프로젝트의 정본이다. 구현 저장소·대화·실험 결과는 작업 큐의 작업과 증거에 연결될 때에만 공식 진행 상태로 인정한다.
- 새 작업을 시작하기 전 작업 큐에서 상태·의존성·차단 사유를 읽고, 작업을 맡으면 **진행 중**으로 바꾼다.
- 완료에는 결과물 경로·커밋·실행 명령·측정값 등 재현 가능한 **결과물·증거**가 필요하다. 증거 없이 완료로 바꾸지 않는다.
- 요구사항·아키텍처·임계치가 바뀌면 먼저 이 기획서 본문을 고치고 영향받는 작업을 갱신한다. 본문은 변경 이력이 아니라 현재 확정 상태만 담는다.
- 상태 충돌이나 외부 의존성은 **차단**으로 표시하고, 추측으로 다음 단계를 완료 처리하지 않는다.
