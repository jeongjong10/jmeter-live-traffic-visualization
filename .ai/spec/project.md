# 프로젝트 정의서 (JMeter Live Traffic)

## JMeter 부하 테스트 실시간 흐름 관제 도구

JMeter로 구성한 비즈니스 프로세스(사용자 흐름) 테스트가 실행되는 동안, 가상 사용자가 어느 단계에 있고 부하와 지연·오류가 어디에 몰리는지를 화면에서 실시간으로 관제하고, 끝난 실행을 다시 재생해 분석하는 도구다.

이 문서는 노션 「JMeter 실시간 부하 흐름 시각화 도구 기획서」 하위의 사본 페이지와 1:1로 유지한다. 작업 상태·결정 이력의 정본은 노션 기획서와 실행 작업 큐다.

---

## 1. 해결하려는 현실

부하 테스트를 수행하는 사용자는 JMeter에서 로그인 → 조회 → 처리 → 결과 확인처럼 업무 순서를 따르는 테스트 계획(jmx)을 만들고, 여러 가상 사용자로 반복 실행한다. 그러나 JMeter가 기본으로 보여 주는 것은 Sampler별 처리량·응답시간·오류율 같은 집계 수치와 결과 목록이다.

이 방식으로는 실행 중에 다음 질문에 답하기 어렵다. 지금 가상 사용자들은 업무 흐름의 어느 단계에 있는가. 부하가 어느 단계로 이동하고 있으며 어디에서 정체되는가. 지연이나 오류는 언제, 어느 단계에서, 왜 발생했는가. 테스트가 끝난 뒤 그 흐름을 시간순으로 다시 볼 수 있는가.

이 프로젝트는 JMeter 실행 결과를 데이터 원천으로 삼아 이 질문들에 화면으로 답한다.

---

## 2. 목표와 핵심 산출물

### 2.1 목표

1. 기존 jmx를 고치지 않고 Backend Listener 하나만 추가해 연동한다.
2. 실행 중 가상 사용자의 업무 단계 위치와 단계별 부하·지연·오류를 실시간으로 표시한다.
3. 실행이 끝나면 같은 흐름을 시간축으로 재생·탐색한다.
4. 사용자는 주소 하나로 진입해 실시간 관제와 재생을 모두 사용한다.

### 2.2 핵심 산출물

* **리스너 JAR**: JMeter의 `lib/ext`(또는 `user.classpath`)에 넣는 Backend Listener 구현.
* **collector**: 결과 수집·흐름 복원·실행 기록 보관·실시간 전송과 화면 제공을 하나의 프로세스로 수행하는 서버.
* **웹 화면**: 대시보드형 관제·재생 화면(JMeter Live Traffic).
* **검증 자산**: 모의 API와 예제 jmx로 구성한 E2E 시나리오.

---

## 3. 범위와 경계

### 3.1 포함 범위

* JMeter Backend Listener 기반 실시간 결과 수집(샘플 단위)
* 실행 중인 테스트 트리(jmx) 해석과 Thread Group별 단계 목록 구성
* 스레드 이름·라벨·시작 시각을 이용한 가상 사용자 위치 복원
* 단계별 부하(동시 사용자)·1회 호출 응답시간(평균/p95)·오류와 실패 사유(Assertion 메시지) 표시
* 최근 실행 기록 보관과 시간축 재생·요청 단위 이동
* 단일 머신 loopback 환경에서의 실행

### 3.2 제외 범위

* 서버 내부 호출 경로·DB 쿼리 단위 분석(JMeter가 관측하지 않는 영역)
* 여러 JMeter 실행기(분산 테스트)의 통합 관제
* 인증·TLS·원격 노출, 재시도·멱등 전송, 장기 보존 관리
* 요청·응답 본문과 헤더 수집(개인정보 포함 가능성)

---

## 4. 사용 흐름

사용자는 JMeter에서 업무 흐름을 Thread Group과 Sampler 순서로 구성한다. 이 구성이 곧 화면의 단계 목록이 된다. 연동을 위해 사용자가 하는 일은 리스너 JAR을 JMeter에 넣고 Test Plan에 Backend Listener를 하나 추가하는 것뿐이다.

`docker/`에서 `docker compose up -d`로 시스템을 띄우고 `http://127.0.0.1:8765`를 연 상태에서 JMeter 테스트를 시작하면, 리스너가 실행 중인 테스트 트리를 collector에 전송하고 collector는 새 실행 기록을 연다. 이후 들어오는 결과로 화면이 실시간으로 갱신되고, 테스트가 끝나면 실시간 모드는 마지막 시점에서 멈춘다. 사용자는 상단의 실행 기록에서 지난 실행을 골라 재생·탐색한다.

## 5. 시스템 구성

### 5.1 전체 구조

```
 [JMeter 실행 환경]                            [collector 컨테이너: 127.0.0.1:8765]
┌────────────────────────────┐  POST /events   ┌──────────────────────────────────┐
│ JMeter (GUI 또는 -n)       │  POST /api/     │ 수신·정규화                      │
│  ├ 사용자 jmx (무수정)     │    test-tree    │ jmx/테스트 트리 해석 (jmx_plan)  │
│  └ Backend Listener JAR ───┼───────────────▶ │ 사용자 흐름 복원 (flow_tracker)  │
│     비동기 큐·배치 전송     │                 │ 실행 기록 보관   (run_store)     │──▶ Docker 볼륨
└────────────────────────────┘                 │ 실시간 전송      SSE /stream     │      runs/<id>/
                                               │ 로그             logs/collector  │
                                               │ 화면 제공        /app/web        │
                                               └───────────────┬──────────────────┘
                                                               │ 같은 주소 (/, /collector/*)
                                               ┌───────────────▼──────────────────┐
                                               │ 브라우저: JMeter Live Traffic    │
                                               │ KPI·시간축 그래프·업무 흐름·표   │
                                               └──────────────────────────────────┘
```

### 5.2 구성요소별 역할

| 구성요소 | 위치 | 기술 | 역할 |
| --- | --- | --- | --- |
| 리스너 | `src/listener` | Java 21, Maven | `SampleResult`를 계약 JSON으로 정규화해 배치 POST, 테스트 시작 시 실행 중인 테스트 트리 전송, 실패 샘플의 Assertion 메시지 수집 |
| collector | `src/collector` | Python 표준 라이브러리 | 이벤트 수신, jmx 해석, 사용자 위치 복원, 실행 기록 보관, SSE 전송, 빌드된 화면 제공 |
| 화면 | `src/web` | React, TypeScript, Vite, Canvas | 실시간·재생 대시보드. NetViz(MIT)에서 파생 |
| 검증 자산 | `tests/e2e` | Python, JMeter, sh | 모의 API와 예제 jmx로 실행 결과와 화면 데이터의 일치 검증 |

### 5.3 실행 구조

시스템은 collector 컨테이너 하나다. `docker/`에서 `docker compose up -d`를 실행하면 이미지 빌드 단계에서 화면을 만들고, collector가 API·SSE와 화면을 같은 포트로 제공하므로 사용자는 주소 하나로 진입한다. 컨테이너 포트는 호스트의 `127.0.0.1`에만 노출한다. 화면을 개발할 때는 Vite 개발 서버(5174)를 추가로 띄워 HMR을 쓰며, API 호출은 collector로 프록시된다.

환경변수는 두 계층으로 나누고, OS 환경변수 `COMPOSE_ENV_FILES`(예: `.env.dev`)로 환경을 고른다.

| 계층 | 파일 | 키 | 의미 |
| --- | --- | --- | --- |
| 컨테이너 기동 | `docker/.env.*` | `COMPOSE_PROJECT_NAME` | Compose 프로젝트명(컨테이너·볼륨 이름 접두어) |
| 컨테이너 기동 | `docker/.env.*` | `COLLECTOR_PORT` | 호스트 진입 포트(기본 8765) |
| 런타임 | `items/.env.*` | `COLLECTOR_RUN_KEEP` | 보관할 최근 실행 기록 수(기본 5) |

로그는 저장소 루트 `logs/`에 모인다. collector 로그는 `logs/collector/collector.log`, E2E 실행 로그와 JTL은 `logs/e2e/<시나리오>/`다. 실행 기록·등록 계획은 Docker 볼륨에 보관한다.

## 6. 데이터 흐름

1. 리스너는 테스트 시작 시 JMeter가 보유한 테스트 트리(GUI에서 저장하지 않은 변경 포함)를 `POST /api/test-tree`로 보낸다. collector는 이를 해석해 활성 Thread Group별 단계 목록, 반복 단계, 부하 설정, 오류 시 동작을 만들고 새 실행 기록을 시작한다.
2. 리스너는 샘플 결과를 비동기 큐에 모아 `batchSize`(기본 100) 또는 `flushIntervalMillis`(기본 1000ms) 단위로 `POST /events`에 보낸다. 전송은 at-most-once이며 실패한 배치는 로그만 남기고 버린다.
3. collector는 각 결과의 스레드 이름·라벨·시작 시각으로 그 가상 사용자의 단계 위치를 복원한다. 같은 라벨은 트리 위치로 구분하고, 결과가 도착하면 같은 사용자의 다음 단계를 처리 중(추정)으로 표시한 뒤 실제 결과가 오면 실측으로 확정한다.
4. collector는 이벤트를 실행 기록(`runs/<id>/events.ndjson`, 당시 계획은 `meta.json`)에 남기고, 연결된 화면에 SSE로 묶어(`batch`) 보낸다. 화면이 밀리면 `resync`로 전체 재로딩을 지시하며 이벤트를 버리지 않는다.
5. 화면은 이벤트를 누적 반영해 KPI·시간축 그래프·업무 흐름·집계 표를 그리고, 재생 시에는 실행 기록(`GET /api/runs/<id>`)을 같은 방식으로 다시 그린다.

## 7. 측정값과 추정 표현의 구분

화면의 수치(처리량·응답시간·오류)는 JMeter가 측정한 샘플 결과에서만 계산한다. 다음 단계의 처리 중 표시는 응답 전 상태를 알 수 없는 Backend Listener의 한계를 보완하는 추정이며, 화면에서 점선 등으로 실측과 구분한다. 토큰 이동 같은 애니메이션은 읽기 위한 시각 표현이며 실제 요청 수를 뜻하지 않는다.

단계의 응답시간은 1회 호출 기준(평균·p95)으로 계산한다. 같은 사용자의 반복 호출을 누적하면 그 API의 평가가 왜곡되기 때문이다. 노드 색은 평소 대비(그 API의 지금 응답시간 ÷ 이번 실행에서의 평소 응답시간인 중앙값)로 칠해, 그 API가 평소보다 느려질 때 붉게 보이게 한다. 다른 API와 비교하지 않는다. 사용자가 오래 머물기만 하는 반복 단계는 동시 사용자가 많아도 응답이 평소대로면 파랗다. 동시 사용자 수는 숫자로 따로 표시한다. 단계 간 비교 배지(평균 최대, p95 최대, 오류)는 실행 중의 일시적 값이 아니라 테스트 종료 후 최종 결과로만 단다. 테스트가 끝나고 재생 위치가 기록 끝인 완료 상태에서는 마지막 순간 값 대신 각 단계의 최대치(최대 동시 사용자, 1초 구간 최대 처리량, 평소 대비 최대, 최종 평균·p95·오류)를 정적으로 표시한다.

## 9. 프로그램 형태와 대안

현재 형태는 **웹 화면 하나와 리스너 JAR 하나**다. 사용자 쪽 변경은 Backend Listener 추가로 한정하고, 관제와 재생은 브라우저 주소 하나에서 수행한다.

다음 두 형태는 대안으로 설계만 해 둔다.

* 웹에서 JMeter 실행: 화면에서 jmx를 올리고 실행 버튼으로 JMeter(-n)를 띄워 실행까지 한곳에서 수행한다. `design-web-jmeter-runner.md` 참조.
* JMeter 내장(GUI) 플러그인: JMeter GUI 안에서 관제 화면을 연다. `design-jmeter-gui-plugin.md` 참조.

## 10. 한계

* 관측 범위는 JMeter가 호출한 요청 결과다. 서버 내부 흐름은 별도 계측 없이는 그리지 않는다.
* 단일 JMeter 실행기, loopback, at-most-once 전송을 전제로 한다.
* 지원하는 테스트 요소는 HTTP Sampler, Loop/If Controller, Flow Control Action이며 그 외 요소는 화면에 경고로 표시한다.
* 1초 버킷 집계와 화면 반영 지연 측정은 아직 구현하지 않았다.
